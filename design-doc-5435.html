Design Document: Forced Conflicting Coin Selection Optimization

Author: Muhammad Hamza
Target Repository: lightningdevkit/rust-lightning
Tracking Issue: Issue 5435 (Forgejo)
Affected Component: lightning/src/util/wallet_utils.rs

1. Engineering Background & Skill Alignment

Resolving Issue 5435 requires a convergence of systems-level Rust programming, Bitcoin transaction construction mechanics, and algorithmic optimization under strict state invariants.

1.1 Systems-Level Rust Engineering

  • Data Structure Manipulation: Low-overhead collection processing within lightning/src/util/wallet_utils.rs utilizing nested hashing (HashMap), double-ended queues (VecDeque), composite ordering keys with lexicographical comparison (sort_unstable_by_key), and core::cmp::Reverse wrappers.
  • Invariant & State Safety: LDK maintains a locked-coin tracking table in memory (locked_utxos: Mutex<HashMap<OutPoint, Option<ClaimId>>>). Manipulating these entries during coin selection requires clean lock management, avoiding deadlocks, and maintaining rollback integrity if downstream lookups fail.
  • Zero Allocations & no-std Compliance: Core crates in LDK target constrained environments. Modifications avoid unbounded allocations, unnecessary cloning, and external runtime dependencies.

1.2 Bitcoin Protocol & Transaction Construction

  • UTXO Effective Value: Accurate selection depends on calculating the effective value of an output (value - fee_for_weight), properly factoring in witness satisfaction weights (P2WPKH, P2TR, P2WSH), legacy script overhead, and dust limits.
  • Mempool Replacement (RBF) & Claim Conflict Dynamics: When a wallet's liquid UTXOs are exhausted, choosing which locked UTXO to borrow effectively initiates an in-protocol double-spend. Understanding how package claiming (lightning/src/chain/package.rs) handles displaced claim transactions—and how RBF fee escalation cascades—is essential to evaluating displacement policies.

2. Problem Context & Root Cause Analysis

The Specification Invariant

"If all of the available UTXOs have already been assigned to other claims, implementations must be willing to double spend their UTXOs. The choice of which UTXOs to double spend is left to the implementation, but it must strive to keep the set of other claims being double spent to a minimum."

— CoinSelectionSource protocol requirement

The Failure Mode

Wallet::select_confirmed_utxos_internal falls back to force_conflicting_utxo_spend = true only after attempts using unreserved coins have failed. In this fallback state, all locked UTXOs were previously sorted globally by effective value alone, completely oblivious to the owning ClaimId. As a result, small coins from multiple independent claims were greedily fragmented and displaced.

// Concrete Example
* Claim A holds: [1,000 sat, 3,000 sat]
* Claim B holds: [1,100 sat]
* Incoming Claim C requires: 1,800 sat

Previous Behavior: Sorts [1,000 (A), 1,100 (B), 3,000 (A)] → Takes 1,000 + 1,100. Displaces BOTH Claim A and Claim B.
Optimized Behavior: Takes 3,000 sat coin from Claim A. Displaces ONLY Claim A.

3. Recommended Architecture: Value-Group Greedy Sort

To maintain strict no-std boundaries and avoid interface leakage into external wallet abstractions, the design employs a hierarchical composite sorting key:

Composite Key = (IsConflicting, Reverse(GroupTotalValue), ClaimId, EffectiveValue)
  1. Phase 1: Aggregate Power — Precompute total effective purchasing power per conflicting claim in a single linear pass.
  2. Phase 2: Priority Grouping — Unlocked coins retain highest priority; conflicting coins are grouped by claim and sorted so highest-power claims evaluate first.
  3. Phase 3: Greedy Linear Walk — Single-claim fulfillment is achieved without recursive backtracking or external dependency leakage.

4. Rust Implementation Specification

// 1. Identify conflicting claim ownership
let conflicting_claim_id = |utxo: &Utxo| {
    locked_utxos
        .get(&utxo.outpoint)
        .and_then(|utxo_claim_id| *utxo_claim_id)
        .filter(|utxo_claim_id| Some(*utxo_claim_id) != claim_id)
};

// 2. Pre-compute total effective purchasing power per conflicting claim
let mut conflicting_claim_values = new_hash_map();
for (utxo, fee_to_spend_utxo) in &eligible_utxos {
    if let Some(c_id) = conflicting_claim_id(utxo) {
        let effective_value = utxo.output.value - *fee_to_spend_utxo;
        conflicting_claim_values
            .entry(c_id)
            .and_modify(|val| *val += effective_value)
            .or_insert(effective_value);
    }
}

// 3. Composite Sort: Unlocked coins first, richest conflicting claims first
eligible_utxos.sort_unstable_by_key(|(utxo, fee_to_spend_utxo)| {
    let effective_value = utxo.output.value - *fee_to_spend_utxo;
    let conflicting_claim = conflicting_claim_id(utxo).map(|c_id| {
        (
            core::cmp::Reverse(*conflicting_claim_values.get(&c_id).unwrap()),
            c_id.0,
        )
    });
    (conflicting_claim, effective_value)
});
